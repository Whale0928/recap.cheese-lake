# 0003. 수신자를 지정하는 리캡 공유

## Status

Draft, 2026.10.23. 데이터 모델 초안이며 화면·API·권한 검사·만료 정리는 아직 구현하지 않았다.

## Context

시청자는 자신의 채널 상세 기록에서 해당 스트리머에게 리캡을 공유할 수 있다.
스트리머는 치지직으로 로그인한 뒤 자기 리캡과 별개로 공유받은 기록을 확인한다.
공유받을 스트리머가 Recap을 이용한 적이 없어 계정 매칭 행이 없을 수 있다.
전체 채널 기록을 공유하면 다른 방송에서의 활동도 드러나므로 범위를 명시적으로 선택해야 한다.

## Decision

`recap.recap_shares`에 소유자·수신자 한 쌍의 현재 공유 승인 하나를 저장한다.
공유 변경 이력을 저장하는 로그 테이블은 만들지 않는다. 화면의 위치와 구성은 추후 정한다.

- 소유자는 인증 세션의 채널 ID로 결정한다. 수신자는 공유 대상 스트리머의 채널 ID다.
- 소유자는 `chzzk_accounts`를 참조하며 계정 삭제 시 공유도 삭제한다.
  수신자는 미가입 상태를 허용하므로 계정 FK를 두지 않는다.
- `share_scope`는 `channel` 또는 `all`이다. `channel`은 수신자 방송에서 작성한 기록만,
  `all`은 동의한 전체 채널 기록을 뜻한다. 기본 선택은 `channel`로 계획한다.
- 기간은 포함 시작 `period_from`과 제외 종료 `period_to`로 저장한다.
  서버가 승인 항목만 구성한 `snapshot`을 저장하며 이후 활동을 자동 추가하지 않는다.
  채팅 원문, 서비스 접속·활동 로그와 인증정보는 포함하지 않는다.
- 동의 시각과 만료 시각을 저장한다. 상대·항목·기간·목적·보유 및 이용 기간·동의 거부권을
  안내하고 동의받는다. 범위를 바꿀 때에는 미리보기와 동의를 다시 거친다.
- 소유자와 수신자가 같거나, 기간이 역전되거나, 만료가 유효하지 않거나,
  허용하지 않은 항목이 포함된 요청은 애플리케이션에서 거절한다. CHECK 제약조건은 두지 않는다.
- 수신함과 상세 조회는 인증된 수신자에게만 허용한다. UUID나 URL을 아는 것만으로는
  열람할 수 없다. 소유자와 수신자의 처리 제외 상태도 검사한다.
- 재공유나 방송 공개는 이 승인의 범위에 포함하지 않는다. 이미 열람·캡처된 사본의
  원격 회수는 보장하지 않는다. 수신자는 공유받기를 거부하거나 수신 항목을 제거할 수 있어야 한다.
- 해제는 승인 행과 snapshot을 삭제한다. 만료는 정리 작업 실행 여부와 관계없이 즉시
  열람을 거절하고 지체 없이 행과 snapshot을 정리한다. 관련 캐시도 무효화한다.
  같은 상대에게 다시 공유할 때는 현재 승인만 교체하며 새 동의와 snapshot을 사용한다.

운영 관리 화면은 Lab에 둔다. 공유 설정과 삭제 처리는 Recap 내부 관리 API가 담당하고,
Recap 스키마 및 마이그레이션의 소유권도 Recap에 둔다. Lab 서버가 테이블을 직접 수정하지 않는다.
서비스 간 인증과 관리자 권한 검사를 각각 수행하며, Lab 로그인만으로 일반 사용자의
비공개 리캡 열람 권한이 생기지 않는다. 관리 API의 구체적인 계약과 화면은 이번 범위에 없다.

## Consequences

사용자는 공개 URL 대신 특정 스트리머에게 제한된 기록을 전달할 수 있다.
스냅샷 저장으로 공유 범위가 이후 활동에 따라 늘어나지 않지만 별도 개인정보 사본이 생긴다.
삭제 요청 시 원본뿐 아니라 공유 스냅샷과 캐시까지 정리해야 한다.

테이블 생성만으로 공유 기능이나 접근 제어가 동작하지 않는다. API를 추가하기 전에
snapshot의 필드·크기 제한과 만료 선택지, 수신 거부 방식을 확정해야 한다.
한 소유자·수신자당 현재 승인 하나만 지원하며 여러 기간의 공유를 동시에 보관하는 기능은 포함하지 않는다.
