- subscription_known 은 **08-26부터**만 채워진다 (08-26 82.98%, 08-27 이후 99.31~99.48%). 08-25 이전은 전부 0.

## E1. 구독 개월

**판정: 부분 가능** — 값은 정확하고 표본 전원에서 산출되지만, 실효 관측이 5일뿐이다.

근거 수치.

- chat_subscription_state: 15,620,419행, 유저 284,624명, bucket_at 2026-08-23 19:49 ~ 08-30 22:42. 단 08-25 이전은 66행 → 실효 08-26~30.
- sub_months>0 ↔ sub_tier>0 이 정확히 일치한다 (둘 다 6,388,027행, 40.9%). "확인된 비구독"은 sub_months=0, sub_tier=0 으로 남는다.
- sub_months 분포: 중앙값 0, p90 20, p99 61, 최대 191. sub_months>0 인 유저 68,135명 / 284,624명 (23.9%).
- 표본 유저별 (channel_id, max(sub_months)) 산출 — 전원 값 나옴:
  - ECD284: 채널 B044E3 에서 25개월 (tier 2, 상태행 1,764)
  - D1BF1B: 채널 475313 에서 29개월 (tier 2, 상태행 1,501)
  - 08F3A5: 채널 64D760 에서 26개월 (tier 1), 채널 B044E3 에서 7개월, 나머지 3채널은 확인된 비구독(0)
  - 40588D: 2채널에서 각 5개월 (tier 1/2), 3채널 비구독
  - 1E5ED2: 발화 150여 채널 중 30채널에서 1~15개월, 나머지는 비구독 — 다채널 유저도 채널별로 분리돼 나온다.

subscription_known 과의 관계: chat_messages 에서 subscription_known=1 인 행의 (sub_tier, sub_months)와 state 의 값은 같은 관측이다(아래 E2의 전수 비교). state 는 그것을 분 버킷으로 접어 둔 압축본이고, subscription_known=0 인 발화는 어느 쪽에도 구독 정보가 없다.

막는 것과 해소 시점.

- 기간: 리캡 대상 기간(8월 전체) 중 구독 상태를 아는 것은 08-26 이후 발화뿐이다. 08-26 이후 발화가 없는 유저는 값이 없다. sub_months 는 누적 개월이라 한 번만 관측돼도 "n개월째 구독"은 말할 수 있으므로, 5일 안에 발화한 유저에 한해 조각이 성립한다. 수집이 계속되는 한 커버리지는 날마다 자연 해소된다.

실제 질의.

```sql
SELECT min(bucket_at), max(bucket_at), uniqExact(user_id), count(),
  countIf(sub_months = 0), countIf(sub_months > 0),
  countIf(sub_tier = 0), countIf(sub_tier > 0)
FROM chat_subscription_state;

SELECT quantilesExact(0.5, 0.9, 0.99)(sub_months), max(sub_months),
  uniqExactIf(user_id, sub_months > 0), uniqExact(user_id)
FROM chat_subscription_state;

SELECT hex(user_id), hex(channel_id), max(sub_months), max(sub_tier), count()
FROM chat_subscription_state
WHERE user_id IN (unhex('...'), ...)  -- 표본 5명
GROUP BY user_id, channel_id ORDER BY 1, 3 DESC;

SELECT toDate(bucket_at) AS d, count(), uniqExact(user_id),
  round(100.0 * countIf(sub_tier > 0) / count(), 2)
FROM chat_subscription_state GROUP BY d ORDER BY d;
```

## E2. 구독자로 친 말

**판정: 부분 가능** — 산출은 되고 표본 값도 나온다. E1과 같은 5일 제약.

원천 판정: **둘 다 맞고, 용도가 다르다.** 08-28 하루 전수 비교에서 (user_id, channel_id)별 max(sub_tier)가 messages(subscription_known=1) 237,761쌍 vs state 237,811쌍, 교집합에서 일치 237,760 / 불일치 1. 두 테이블은 같은 관측의 다른 해상도다.

- "구독자로 친 말이 몇 개인가"(메시지 수 세기)는 **chat_messages (subscription_known=1 AND sub_tier>0)** 가 원천이다. state 는 분 버킷으로 접혀 있어 메시지 수를 잃는다.
- "구독 상태·개월이 얼마인가"(상태 조회)는 **chat_subscription_state** 가 낫다. 행 수가 1/3이고 정렬 키가 (channel_id, live_id, bucket_at, user_id)라 채널·유저 조회가 빠르다.

근거 수치.

- 커버리지: subscription_known=1 은 08-26 82.98% → 08-27 이후 99.31~99.48%. 그중 sub_tier>0 은 일자별 44.8~47.5%.
- 표본 유저별 (전체 발화 / known / 구독자로 친 말 / known 대비 비율):
  - 40588D: 29,241 / 18,056 / 18,015 / 99.8%
  - ECD284: 34,898 / 18,218 / 18,218 / 100%
  - 08F3A5: 28,702 / 17,685 / 17,675 / 99.9%
  - D1BF1B: 27,481 / 14,531 / 14,531 / 100%
  - 1E5ED2: 32,928 / 22,094 / 4,818 / 21.8% (봇, 다채널이라 비구독 채널 발화가 많음)

막는 것: E1과 동일한 기간 제약. 전체 발화 대비 분모를 잡으면 known=0 인 08-25 이전 발화가 전부 "모름"으로 빠진다. 조각 문구를 "구독 상태를 확인한 발화 중 n%"로 잡으면 지금도 성립한다.

실제 질의.

```sql
WITH m AS (
  SELECT user_id, channel_id, max(sub_tier) AS t
  FROM chat_messages
  WHERE subscription_known = 1 AND toDate(sent_at) = '2026-08-28'
  GROUP BY user_id, channel_id
), s AS (
  SELECT user_id, channel_id, max(sub_tier) AS t

SELECT (SELECT count() FROM m), (SELECT count() FROM s),

  (SELECT count() FROM m INNER JOIN s ON m.user_id = s.user_id AND m.channel_id = s.channel_id WHERE m.t != s.t);
-- 237761 / 237811 / 237760 / 1 (1.1초)

    / countIf(subscription_known = 1), 1)
FROM chat_messages
WHERE user_id IN (unhex('...'), ...)  -- 표본 5명
GROUP BY user_id;
```

## F1. 자주 쓴 말

**판정: 가능** — 형태소 분석 없이 공백 분리 + 반복 문자 정규화만으로 유저별 상위 토큰이 유의미하게 나온다. 단 선별 로직 없이는 상위가 범용 필러로 쏠린다.

근거 수치.

- 전체 상위 토큰(08-28 하루, 플레이스홀더 제거 후 공백 분리, 1.4초): `?` 139,399 / `ㅋㅋ` 109,097 / `캬` 90,229 이하 상위 20개 중 12개가 `ㅋ` 반복 변형. 정규화 없이는 ㅋㅋㅋ 길이별로 순위가 쪼개진다.
- `ㅋ{2,}→ㅋㅋ`, `ㅎ{2,}→ㅎㅎ`, `[ㅠㅜ]{2,}→ㅠㅠ`, `!{2,}→!`, `?{2,}→?` 체인 치환 후 표본 유저별 상위 5토큰 (질의 0.23초):
  - 08F3A5: ㅋㅋ 9,790 / ㄹㅇ 1,637 / 캬 988 / 오 734 / ㅔㅔ 438
  - ECD284: ㅋㅋ 13,339 / 네넹 1,298 / 넹 1,190 / ㅇㅎ 1,138 / ㄹㅇ 1,013
  - D1BF1B: 진짜 986 / ㅋㅋ 768 / ㅠㅠ 465 / ㄹㅇ 419 / 그냥 390
  - 40588D: ㅋㅋ 3,860 / 캬 1,479 / 오 1,276 / ? 1,162 / 헉 677
  - 1E5ED2: `번째` 9,383 / `-->` 8,576 / `출석체크입니다.` 6,380 — 정형 문구 반복으로 봇임이 드러난다. 봇 필터링에도 이 조각이 쓸모 있다.
- 유저 간 차이가 실제로 드러난다 (네넹/넹 vs 진짜/그냥 vs 캬/헉). 조각으로 성립한다.

주의점 (산출을 막지는 않음).

- re2는 역참조를 지원하지 않아 `(.)\1{2,}` 패턴이 안 된다. 문자별 체인 치환으로 우회했다.
- 상위 1~2위는 거의 항상 ㅋㅋ 계열이다. "자주 쓴 말"을 재미있게 만들려면 전역 빈도 대비 특이도(로그오즈 등)로 뽑거나 필러 사전을 빼야 한다. 이는 제품 결정이지 데이터 제약이 아니다.
- ClickHouse `tokens()` 는 비영숫자 분리라 한국어 어절이 깨진다. `splitByChar(' ', ...)` 가 맞다.

실제 질의.

```sql
-- 전체 상위 토큰 (하루)
SELECT token, count() AS cnt, uniqExact(user_id) AS users
FROM chat_messages
ARRAY JOIN splitByChar(' ', replaceRegexpAll(body, '\\{:[^:{}]+:\\}', '')) AS token
WHERE token != '' AND toDate(sent_at) = '2026-08-28'
GROUP BY token ORDER BY cnt DESC LIMIT 20;

-- 표본 유저별 상위 5토큰 (정규화 포함)
SELECT uid, tok, cnt FROM (
  SELECT hex(user_id) AS uid, tok, count() AS cnt,
    row_number() OVER (PARTITION BY uid ORDER BY count() DESC, tok) AS rn
  FROM (
    SELECT user_id,
      replaceRegexpAll(replaceRegexpAll(replaceRegexpAll(replaceRegexpAll(replaceRegexpAll(token,
        'ㅋ{2,}', 'ㅋㅋ'), 'ㅎ{2,}', 'ㅎㅎ'), '[ㅠㅜ]{2,}', 'ㅠㅠ'), '!{2,}', '!'), '\\?{2,}', '?') AS tok
    FROM chat_messages
    ARRAY JOIN splitByChar(' ', replaceRegexpAll(body, '\\{:[^:{}]+:\\}', '')) AS token
    WHERE token != '' AND user_id IN (unhex('...'), ...)  -- 표본 5명
  )
  GROUP BY uid, tok
) WHERE rn <= 5 ORDER BY uid, cnt DESC;
```

## F2. 이모티콘

**판정: 가능** — 6.02%는 (a) 이모티콘 없는 메시지가 대부분이라 정상이다. 수집 누락이 아니다.

판정 근거 (이 태스크의 핵심).

- body 의 `{:code:}` 플레이스홀더 존재율과 emoji_codes 채움율이 일자별로 소수점 둘째 자리까지 일치한다 (08-22 5.34%=5.34%, 08-29 6.74%=6.74% 등 전 일자).
- 불일치는 45.8M 행 중: 플레이스홀더가 있는데 emoji_codes 가 빈 행 452 (엄격 패턴 `\{:[a-zA-Z0-9_]+:\}` 기준 446), 반대 방향 1행. 0.001% 수준으로, 유저가 문자 그대로 `{:` 를 타이핑한 경우와 구분되지 않는 잡음이다. 파서가 body 에서 찾은 것과 배열에 넣는 것이 같은 소스라는 뜻이다.
- 채움율이 낮은 이유는 사용 분포다: 이모티콘을 한 번이라도 쓴 유저 109,282 / 343,389 (31.82%). 쓴 유저 안에서도 중앙값 4개, p90 48, p99 373으로 소수 유저에 몰려 있다.
- 상위 코드(전 기간, 0.36초): `d_126` 103,582회(유저 21,128), `d_91` 87,409, `d_54` 77,411, `d_47` 68,622, `d_116` 56,633 … 상위 15개가 모두 `d_*`(플랫폼 기본 이모티콘)이고, 유저별 상위로 내려가면 채널 전용 코드가 나온다.
- 표본 유저별 (이모티콘 메시지 수 / 전체 / 상위 3코드):
  - 40588D: 2,255 / 29,241 / siyo 계열
  - ECD284: 1,392 / 34,904 / shiray22 계열
  - D1BF1B: 222 / 27,485 / ellie 계열
  - 08F3A5: 162 / 28,705 / shibuki 계열
  - 1E5ED2: 0 (봇) — "이모티콘 0개"도 조각 문구로 성립한다.

막는 것: 없음. "가장 많이 쓴 이모티콘", "이모티콘파 vs 텍스트파" 모두 지금 데이터로 산출된다. 코드→이미지 매핑 테이블이 레이크에 없다는 점만 렌더링 단계 숙제로 남는다.

```sql
GROUP BY user_id;
```

## F3. 말의 길이

**판정: 가능** — 단, 플레이스홀더 제거 없이는 크게 왜곡된다. 제거 로직을 조각 정의에 포함해야 한다.

근거 수치.

- 전체 평균 lengthUTF8(body) = 11.3자, 분위 p50 7 / p90 22 / p99 85. (전제의 "평균 24.9자"는 바이트 기준 length() 로 추정된다 — 한글 UTF-8 3바이트를 감안하면 두 수치가 정합한다. 조각에는 lengthUTF8 을 써야 한다.)
- 왜곡의 크기: 이모티콘 없는 메시지 평균 8.8자 vs 이모티콘 메시지 평균 51.0자. 그런데 이모티콘 메시지에서 플레이스홀더를 제거하면 평균 0.6자 — **이모티콘 메시지의 94.8%는 이모티콘 외 내용이 없다.** `{:cheer100:}` 같은 코드가 10~20자를 차지해 "긴 말"처럼 보이는 것뿐이다.
- 표본 유저별 (원본 평균 / 제거 후 평균 / 제거 후 p50·p90):
  - 40588D: 7.0 / 3.9 / [3, 8]
  - ECD284: 9.8 / 6.1 / [6, 12]
  - 08F3A5: 8.7 / 8.4 / [7, 16]
  - D1BF1B: 8.9 / 8.2 / [8, 14]
  - 1E5ED2: 33.2 / 33.1 / [33, 57] (봇의 정형 문구)
  - 이모티콘을 많이 쓰는 40588D 는 제거 전후가 7.0→3.9로 절반 가까이 줄어든다. 왜곡이 유저별로 다르게 걸리므로 제거는 필수다.

막는 것: 없음. 조각 정의만 "플레이스홀더 제거 후 lengthUTF8" 로 고정하면 된다. 이모티콘 전용 메시지(제거 후 0자)를 분모에 넣을지는 제품 결정.

실제 질의.

```sql
SELECT round(avg(lengthUTF8(body)), 1),
  quantilesExact(0.5, 0.9, 0.99)(lengthUTF8(body)),
  round(avgIf(lengthUTF8(body), empty(emoji_codes)), 1),
  round(avgIf(lengthUTF8(body), notEmpty(emoji_codes)), 1),
  round(avgIf(lengthUTF8(replaceRegexpAll(body, '\\{:[^:{}]+:\\}', '')), notEmpty(emoji_codes)), 1),
  round(100.0 * countIf(notEmpty(emoji_codes)
    AND empty(replaceRegexpAll(body, '\\{:[^:{}]+:\\}|\\s', '')))
    / countIf(notEmpty(emoji_codes)), 1)
FROM chat_messages;  -- 11.3 / [7,22,85] / 8.8 / 51.0 / 0.6 / 94.8 (1.9초)

SELECT hex(user_id), round(avg(lengthUTF8(body)), 1),
  round(avg(lengthUTF8(replaceRegexpAll(body, '\\{:[^:{}]+:\\}', ''))), 1),
  quantilesExact(0.5, 0.9)(lengthUTF8(replaceRegexpAll(body, '\\{:[^:{}]+:\\}', '')))
FROM chat_messages
WHERE user_id IN (unhex('...'), ...)  -- 표본 5명
GROUP BY user_id;
```

## F4. 어디서 말했나

**판정: 가능** — 값이 깨끗하고 표본 유저별로도 바로 나온다.

근거 수치.

- 값 종류는 4가지뿐: `PC` 31,616,949 (68.98%) / `AOS` 10,322,326 (22.52%) / `IOS` 3,650,894 (7.97%) / 빈 문자열 243,724 (0.53%).
- 빈 문자열 유저 23,686명이 있으므로 조각에서는 "알 수 없음" 처리 또는 제외가 필요하다.
- 표본 유저별: 08F3A5 = PC 28,104 + AOS 601 (기기 전환이 드러남), 40588D = AOS 29,239 (모바일 전용), D1BF1B = PC 27,438 + AOS 53, ECD284 = PC 34,912 (PC 전용). "너는 PC파 / 폰파" 문구가 그대로 성립한다.

막는 것: 없음.

실제 질의.

```sql
SELECT os_type, count(), round(100.0 * count() / (SELECT count() FROM chat_messages), 2),
  uniqExact(user_id)
FROM chat_messages GROUP BY os_type ORDER BY 2 DESC;

SELECT hex(user_id), os_type, count()
FROM chat_messages
WHERE user_id IN (unhex('...'), ...)  -- 표본 4명
GROUP BY user_id, os_type ORDER BY 1, 3 DESC;
```

## G1. 한 줄로 줄이면

**판정: 가능** — LLM 입력으로 넘길 집계값이 위 조각들에서 전부 산출된다. 새 질의는 없다.

점검 결과, 유저당 입력 벡터로 쓸 수 있는 값:

- 발화량·시간대·채널: chat_trace (판정 A/B 범위, 22일치)
- 구독: 채널별 max(sub_months), max(sub_tier), 구독자 발화 비율 (E1·E2, 5일치)
- 상위 토큰: 정규화 후 상위 N (F1)
- 이모티콘: 사용 메시지 수, 상위 코드 (F2)
- 길이: 제거 후 평균·분위 (F3)
- 기기: os_type 분포 (F4)
- 채널 문맥: live_census 의 name·category (기확인 98.71%)

제약 전파: 구독 값은 5일치라는 단서를 프롬프트에 함께 넘기거나 빼야 한다. 본문 원문은 넘기지 않는다는 원칙과도 정합 — 위 값은 모두 집계값이다. 상위 토큰이 사실상 발화 스타일을 노출하므로, 프롬프트에 넣을 토큰은 필러(ㅋㅋ 등) 위주로 제한할지 제품에서 정해야 한다.

## G2. 공유 카드

**판정: 가능(종속)** — 새 원천이 필요 없다. 카드에 올릴 수치는 전부 다른 조각의 산출물이므로, E·F 각 조각의 판정과 제약(특히 구독 5일치)이 그대로 종속된다. 데이터 관점에서 추가로 막는 것은 없다.
