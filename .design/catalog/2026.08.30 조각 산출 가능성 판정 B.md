# 2026.08.30 조각 산출 가능성 판정 B — 시간축(C)과 live_census(D)

실제 ClickHouse 질의로 판정했다. 표본은 chat_trace 상위 발화 유저 5명
(`ECD2847E…`, `1E5ED2A8…`, `40588DD1…`, `08F3A5B8…`, `D1BF1B56…`)이다.
chat_trace 는 ReplacingMergeTree 이므로 sum(msg_count) 이 필요한 질의는
(channel_id, bucket_at, user_id) 로 접고 argMax(msg_count, ingested_at) 을 썼다.
일자·시간대 존재 여부와 min/max 만 쓰는 질의는 중복 행이 결과를 바꾸지 않으므로 접지 않았다.

## 전제를 뒤집는 발견 두 가지

**1. chat_trace 의 실질 기간은 22일이 아니라 9일이다.**
2026-08-08~08-21 은 14일 합계 550건(하루 7~387건)의 테스트성 흔적이고,
08-15~17 은 아예 비어 있다. 본 수집은 08-22(244만 건)부터다.
C 계열 전체의 분모는 9일로 봐야 한다. 상위 발화 유저의 활동일이 전원 9일인 것도 이 때문이다.

**2. chat_trace.live_id 는 100% 채워져 있다.**
사전 정보의 "live_id 47%"는 live_census 쪽 이야기다. chat_trace 25,382,570행 전부 live_id ≠ 0.
따라서 D 계열의 연결 경로는 두 개다: live_id 직접 조인(채팅 행 기준 58.09% 커버),
channel_id+시각 근접 조인(99.43% 커버). live_id 47% 채움은 결정적 제약이 아니다.
결정적 제약은 **live_census 가 6일치(08-24 22:28 ~ 08-30 22:37)뿐**이라는 것 하나다.

## C1 한 해의 결 — 일자별 채팅 수

**판정: 부분 가능**

일자별 집계 자체는 완전하다. 문제는 기간이다.

| 일자 | 접은 후 msg 합 | 유저 수 |
|---|---|---|
| 08-08~08-20 | 총 210 (하루 7~32) | 하루 3~9명 |
| 08-21 | 387 | 153 |
| 08-22 | 2,443,943 | 87,050 |
| 08-23 | 5,839,437 | 146,901 |
| 08-24 | 4,377,757 | 110,607 |
| 08-25 | 4,171,473 | 109,110 |
| 08-26 | 4,914,449 | 129,423 |
| 08-27 | 5,226,710 | 133,508 |
| 08-28 | 5,570,218 | 137,617 |
| 08-29 | 6,671,760 | 162,930 |
| 08-30 | 6,110,240 | 148,461 |

막는 것: 기간. 371칸 연간 격자는 362칸이 빈다. 수집이 계속되면 자연히 풀리는 문제로,
연말 리캡 시점(12월)에는 ~130일치가 쌓인다.

371칸 문제의 표현 방안: (1) 연간 격자를 유지하되 "당신이 온 뒤로"를 시작점으로 오른쪽 정렬해
빈 칸을 여백이 아니라 '아직 오지 않은 날'로 읽히게 한다. (2) 격자를 버리고 9칸 세로 막대
리본으로 축소해 하루하루를 크게 그린다. (3) 지금 단계에서는 격자를 "지난 N일" 상대 기간으로
표기하고 연간 표현은 데이터가 쌓인 뒤 켠다. 현 시점 데이터로는 (2)나 (3)이 정직하다.

```sql
SELECT toDate(bucket_at) AS d, sum(mc) AS msgs, uniqExact(user_id) AS users
FROM (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace GROUP BY channel_id, bucket_at, user_id
)
GROUP BY d ORDER BY d
```

## C2 리듬 — 요일 x 시간대

**판정: 부분 가능** (시간대 축 가능, 요일 축은 표본 부족)

타임존 판정: 서버 timezone() = **Asia/Seoul**. 따라서 `toHour(bucket_at)` 이 이미 KST 이고,
`toTimeZone(bucket_at,'Asia/Seoul')` 은 결과가 같은 무해한 명시다. 저장 자체가 잘못됐을
가능성은 새벽 분포로 기각했다: 시간별 발화 합이 21시 피크(469만), 07시 저점(26.7만)으로
한국 시청 패턴과 정확히 일치한다. 값이 UTC 벽시계였다면 저점이 16시대에 보였어야 한다.

08-22 이후 시간별 분포(접은 후, 요약): 07시 저점 266,865 → 21시 피크 4,699,889 →
0~2시에도 197만~318만으로 두텁다. 시간대 리듬은 그 자체로 조각이 된다.

막는 것: 요일 축. 실질 9일(08-22 토 ~ 08-30 일)에서 토·일은 2회, 월~금은 각 1회 관측이라
"당신은 수요일형" 같은 서술은 1표본 잡음이다. 요일 축은 4주 이상 쌓인 뒤에 켜는 것이 맞다.
지금은 요일을 접고 시간대 24칸 리듬만 쓰는 것을 권한다.

```sql
SELECT toHour(bucket_at) AS h, sum(mc) AS msgs
FROM (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace WHERE bucket_at >= '2026-08-22 00:00:00'
  GROUP BY channel_id, bucket_at, user_id
)
GROUP BY h ORDER BY h
-- 타임존 검증 보조: SELECT timezone()  → Asia/Seoul
```

## C3 가장 시끄러웠던 날

**판정: 가능**

표본 5명 전원에서 최다 발화일, 그날 msg 수, 상위 채널, min/max bucket_at 이 산출된다.

| 유저(hex 앞 8) | 최다 발화일 | 그날 msg | 상위 채널(hex 앞 8) / msg | min~max bucket |
|---|---|---|---|---|
| 1E5ED2A8 | 08-29 | 6,733 | E9FF6A0D / 1,464 | 00:00 ~ 23:59 |
| ECD2847E | 08-24 | 6,395 | B044E3A3 / 6,395 | 00:00 ~ 23:59 |
| D1BF1B56 | 08-24 | 5,452 | 475313E6 / 5,452 | 00:00 ~ 23:59 |
| 40588DD1 | 08-23 | 4,512 | B33C957E / 4,507 | 00:00 ~ 23:59 |
| 08F3A5B8 | 08-29 | 4,504 | 64D76089 / 4,502 | 00:00 ~ 23:59 |

주의: 상위 5명은 전원 00:00~23:59 종일 발화 + 단일 채널 집중이라 봇으로 보인다.
조각 자체는 일반 유저에게도 동일 질의로 산출되므로 판정에는 영향이 없지만,
리캡 상단 노출용 "전체 1위" 류 수치는 봇 필터 없이는 쓰지 않는 것이 좋다.

```sql
WITH folded AS (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace WHERE user_id IN (...)
  GROUP BY channel_id, bucket_at, user_id
),
daily AS (
  SELECT user_id, toDate(bucket_at) AS d, sum(mc) AS day_msgs,
         min(bucket_at) AS first_b, max(bucket_at) AS last_b
  FROM folded GROUP BY user_id, d
)
SELECT hex(user_id), argMax(d, day_msgs), max(day_msgs),
       argMax(first_b, day_msgs), argMax(last_b, day_msgs)
FROM daily GROUP BY user_id
-- 상위 채널: folded 를 (user_id, 최다일) 로 필터해 channel_id 별 sum(mc) ORDER BY DESC
```

## C4 이어짐과 끊김 — 연속 발화일과 공백

**판정: 부분 가능**

산출은 된다. 전 유저 343,022명의 최장 연속 발화일 분포(실측):

| 최장 연속 | 유저 수 |
|---|---|
| 1일 | 166,028 |
| 2일 | 63,448 |
| 3일 | 31,346 |
| 4~6일 | 45,138 |
| 7일 | 5,381 |
| 8일 | 8,990 |
| **9일 (만근)** | **23,016** |
| 10~13일 | 8 |

막는 것: 상한. 실측 최장값은 9일이고 그게 곧 전체 수집 기간이다. 23,016명(6.7%)이
9/9 만근이라 "당신의 최장 연속 N일"은 상위권에서 전부 같은 값이 된다. 10·13일인 8명은
08-21 이전 테스트 흔적이 이어진 것으로 조각에 쓰면 안 된다. 공백(끊김) 쪽도 표본 5명은
전원 만근(max gap 1일)이라 이야기가 없다. 기간이 쌓이면 자연히 풀린다.
지금 쓴다면 "N일 중 M일을 함께했다" 형태의 출석률 서술이 정직하다.

```sql
WITH days AS (
  SELECT user_id, toDate(bucket_at) AS d FROM chat_trace GROUP BY user_id, d
),
per_user AS (
  SELECT user_id,
    arrayMax(arrayMap(p -> length(p),
      arraySplit(x -> x != 1,
        arrayDifference(arrayMap(x -> toInt32(x), arraySort(groupArray(d))))))) AS longest_streak
  FROM days GROUP BY user_id
)
SELECT longest_streak, count() FROM per_user GROUP BY longest_streak ORDER BY longest_streak
```

## C5 밤샘 — 자정을 넘긴 세션

**판정: 가능**

정의(23시대 발화 AND 익일 1시대 발화)로 전수 실측: **93,639 유저-일, 50,852명**
(전체 유저의 14.8%)이 최소 한 번 밤을 넘겼다. 9일 창에서도 조각이 충분히 성립한다.
표본 상위 5명은 종일 발화 패턴이라 전일 해당되며(C3 참조), 이 조각 역시 봇에게
과대 산출되는 성질이 있다.

```sql
WITH hourly AS (
  SELECT user_id, toDate(bucket_at) AS d, toHour(bucket_at) AS h
  FROM chat_trace GROUP BY user_id, d, h
),
h23 AS (SELECT user_id, d FROM hourly WHERE h = 23),
h01 AS (SELECT user_id, d - 1 AS d FROM hourly WHERE h = 1)
SELECT count() AS overnight_user_days, uniqExact(user_id) AS overnight_users
FROM h23 INNER JOIN h01 USING (user_id, d)
```

## C6 가장 긴 하루 — max(bucket) - min(bucket)

**판정: 가능**

유저-일 1,166,076건 전수 실측: p50 94분, p90 1,298분, p99 1,435분, 최대 1,439분(24시간).
하루 한 버킷만 발화해 span=0 인 유저-일이 262,441건(22.5%)이므로 "가장 긴 하루" 서술은
발화 2버킷 이상인 날로 한정해야 한다. 최대치 1,439분은 자정 직후~직전 발화면 나오는 값으로
상위 유저(봇)에서 상시 관측된다. 일반 유저의 개인 최장값은 p90 부근(21시간대)까지 실재한다.

```sql
WITH spans AS (
  SELECT user_id, toDate(bucket_at) AS d,
         (max(bucket_at) - min(bucket_at)) / 60 AS span_min
  FROM chat_trace GROUP BY user_id, d
)
SELECT count(), quantile(0.5)(span_min), quantile(0.9)(span_min),
       quantile(0.99)(span_min), max(span_min), countIf(span_min = 0)
FROM spans
```

## D 공통: live_census 연결 실측

live_census 관측 주기 실측: 705회 관측, 간격 p50 11.5분 / p90 15분 / **최대 16분**
(6일 내내 끊김 없음), 회당 평균 221개 채널. 창은 08-24 22:28 ~ 08-30 22:37.

census 창 내 chat_trace 18,734,238행 기준 연결 커버리지:

- live_id 직접 조인(census live_id ≠ 0 인 것과 매칭): **58.09%**
- channel_id 존재 매칭: **99.99%**
- channel_id + 10분 슬롯(±10분 확장) 시각 근접 매칭: **99.43%** (접은 행 가중)

결론: **live_id 47% 채움은 우회 가능하며 결정적 제약이 아니다.** channel_id+시각 근접
조인이 사실상 전 발화를 카테고리·동접에 잇는다. 유일하게 결정적인 제약은 census 가
6일치라는 것으로, 리캡 대상 기간(9일) 중 08-22~08-24 낮의 발화 약 30%가 census 밖이다.

## D1 카테고리 취향

**판정: 부분 가능** (기술적으로 가능, 6일 창 제약)

channel_id + 10분 슬롯 조인으로 표본 5명 전원의 카테고리 프로필이 실산출된다:

| 유저(hex 앞 8) | 창 내 msg | 카테고리 부여율 | 상위 3 카테고리 | 
|---|---|---|---|
| ECD2847E | 18,954 | 81.01% | 마인크래프트, talk, 로블록스 |
| 08F3A5B8 | 20,210 | 79.96% | 마인크래프트, talk, 고독방송:심 |
| D1BF1B56 | 15,283 | 80.41% | talk, 명조:워더링 웨이브, 림월드 |
| 40588DD1 | 19,641 | 78.69% | talk, FC온라인, 종합 게임 |
| 1E5ED2A8 | 26,811 | 71.40% | talk, 음악/노래, 이터널 리턴 |

표본의 부여율이 전체 매칭률(99.43%)보다 낮은 것은 이들이 방송 종료 후에도 발화하는
종일 봇이기 때문으로, 일반 유저는 더 높게 나올 것이다(미검증 추정). 막는 것: census 6일.
08-24 이전 발화는 카테고리를 얻지 못한다. census 수집이 계속되는 한 시간이 풀어 준다.

```sql
WITH census_slotted AS (
  SELECT channel_id, toStartOfInterval(observed_at, INTERVAL 10 MINUTE) AS s,
         argMax(category, observed_at) AS cat, argMax(viewers, observed_at) AS v
  FROM live_census GROUP BY channel_id, s
),
chat AS (
  SELECT channel_id, toStartOfInterval(bucket_at, INTERVAL 10 MINUTE) AS s,
         user_id, sum(mc) AS msgs
  FROM ( SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
         FROM chat_trace
         WHERE bucket_at BETWEEN '2026-08-24 22:28:00' AND '2026-08-30 22:38:00'
           AND user_id IN (...)
         GROUP BY channel_id, bucket_at, user_id )
  GROUP BY channel_id, s, user_id
)
SELECT hex(user_id), sum(msgs),
  round(100.0 * sumIf(msgs, cat != '') / sum(msgs), 2) AS pct_categorized,
  topKWeightedIf(3)(cat, msgs, cat != '') AS top3
FROM chat LEFT JOIN census_slotted USING (channel_id, s)
GROUP BY user_id
-- 커버리지 검증(99.43%): census (channel_id, s±600초) 슬롯 집합에 대한
-- chat (channel_id, s) IN 매칭을 접은 행 가중으로 집계
```

## D2 방의 크기 — 동접 분포

**판정: 부분 가능** (D1과 동일 구조, 동일 제약)

같은 조인으로 표본 5명의 "발화 시점 동접" 분포가 실산출된다(msg 가중 중앙값 / 최대):
1E5ED2A8 = 114 / 3,054 · 40588DD1 = 552 / 1,793 · D1BF1B56 = 784 / 2,251 ·
ECD2847E = 2,533 / 3,518 · 08F3A5B8 = 4,985 / 13,551. 유저마다 값이 뚜렷이 갈려
"당신은 114명짜리 방에서 떠드는 사람" 서술이 성립한다. 막는 것: census 6일 창과,
viewers 가 10~15분 간격 표본이라는 점(순간 피크는 놓칠 수 있음).

```sql
-- D1 질의에 다음 두 컬럼 추가
round(quantileExactWeighted(0.5)(v, msgs), 0) AS median_viewers,
max(v) AS max_viewers
-- 주: quantileWeighted 는 이 서버(26.7.3)에 없음. quantileExactWeighted 사용
```

## D3 가장 붐빈 방

**판정: 가능(6일 한정)**

실측 최대: **LCK 채널(9381E7D6…), 리그 오브 레전드, 208,845명, 08-29 21:26,
live_id 20810692.** 그 방송(live_id 조인)에 발화 기록이 있는 유저 **13,867명**,
피크 전후 1시간(20:56~21:56)만 좁혀도 **5,076명**이 실재한다.
"당신은 그 방에 있었다" 조각이 그대로 성립한다. 막는 것: census 창 밖(08-24 이전)의
붐빈 방은 알 수 없다는 것뿐이다.

```sql
SELECT hex(channel_id), name, category, viewers, observed_at, live_id
FROM live_census ORDER BY viewers DESC LIMIT 3;

SELECT uniqExactIf(user_id, live_id = 20810692) AS users_same_liveid,
       uniqExactIf(user_id, bucket_at BETWEEN '2026-08-29 20:56:00' AND '2026-08-29 21:56:00') AS users_peak_hour
FROM chat_trace WHERE channel_id = unhex('9381E7D6816E6D915A44A13C0195B202')
```

## D4 방송 길이와 나

**판정: 부분 가능**

census 의 live_id 별 관측 구간(min~max observed_at, 관측 횟수 x ~11.5분)으로 방송 길이를
근사할 수 있다. 여기서는 live_id 47% 채움이 실제로 문제가 된다: census 창 내 채팅이 발생한
방송 4,543개 중 census 에 live_id 가 잡힌 것은 **2,645개(58.2%)** 뿐이다(D1·D2와 달리
길이 측정은 회차 단위 구간이 필요해 channel+시각 우회로 완전히 대체되지 않는다.
channel 단위 세션 재구성으로 일부 보완은 가능하나 이번에는 실측하지 않았다 — 미검증).

겹침은 실재한다. 조인된 2,645개 방송에서 census 구간 p50 259분 vs 채팅 구간 p50 269분,
상관 0.612, 채팅 구간이 평균 34.6분 더 길다(방송 전후 대기 채팅). 표본 유저 ECD2847E 는
창 내 6개 방송 중 3개가 측정 가능했고, 방송 길이 p50 580분에 본인 발화 구간 p50 569분으로
"방송의 거의 전부를 함께한" 서술이 실제 값으로 나온다.

막는 것: (1) census live_id 42% 결측 — 목록 API 가 값을 주지 않은 회차로, 수집측 개선
없이는 시간이 풀어 주지 않는다. (2) 10~15분 관측 간격으로 방송 길이 오차 ±15분.
(3) 6일 창. 종합하면 "길이를 잴 수 있는 방송에 한해" 조각이 성립한다.

```sql
WITH census_lives AS (
  SELECT live_id, count() AS ticks, min(observed_at) AS c_start, max(observed_at) AS c_end,
         (max(observed_at) - min(observed_at)) / 60 AS census_span_min
  FROM live_census WHERE live_id != 0 GROUP BY live_id
),
chat_lives AS (
  SELECT live_id, (max(bucket_at) - min(bucket_at)) / 60 AS chat_span_min
  FROM chat_trace WHERE live_id != 0 GROUP BY live_id
)
SELECT count(), quantile(0.5)(census_span_min), quantile(0.5)(chat_span_min),
       corr(census_span_min, chat_span_min),
       avg(chat_span_min - census_span_min)
FROM census_lives INNER JOIN chat_lives USING (live_id)
-- 커버리지: census 창 내 chat_trace 의 uniqExact(live_id)=4,543 중 census 매칭 2,645
```

  "최고 기록" 조각을 전체 랭킹으로 노출하려면 봇 판별이 선행 과제다. 개인 리캡으로만
  쓰면 문제 없다.
