작성일 2026.08.30. 대상 테이블 development_cheese_lake.chat_trace (ReplacingMergeTree, PARTITION BY toYYYYMM, ORDER BY (channel_id, bucket_at, user_id), PROJECTION by_user). 서버 타임존 Asia/Seoul.

## 전제와 다른 발견 (전 조각 공통)

- **실질 커버리지는 22일이 아니라 약 9일이다.** 2026-08-08~08-21은 일 7~260행 수준의 흔적만 있고, 유의미한 적재는 2026-08-22부터다(일 130만~380만 행). 기간을 쓰는 조각(B3·B6·B7)은 모두 이 절단의 영향을 받는다.
- **데이터가 계속 적재 중이다.** 조사 도중 count()가 25,377,846 → 25,397,439로 늘었다. 같은 유저의 수치가 질의 시점에 따라 수십 건 단위로 달라지므로, 리캡 산출 시에는 기간 상한을 고정해야 한다.
- 중복 접기(GROUP BY channel_id, bucket_at, user_id + argMax(msg_count, ingested_at))를 포함해도 전량 집계가 모두 13초 이내였다. 성능은 어떤 조각에서도 장애물이 아니다.

표본 유저(전량 접기 후 총 채팅 수 상위 5명):

```sql
SELECT hex(user_id) AS uid, sum(mc) AS total_msgs
FROM (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace
  GROUP BY channel_id, bucket_at, user_id
)
GROUP BY user_id ORDER BY total_msgs DESC LIMIT 5
```

| uid | total_msgs |

| 1E5ED2A8…C4E1 | 33,117 |
| 40588DD1…3F75 | 28,868 |
| 08F3A5B8…2BE6 | 27,851 |

1E5E 유저는 158개 채널·같은 분에 다채널 발화(8,232분 vs 채널-분 18,332)로 봇 성격이 짙다. 리캡 모수에서 이런 계정을 거를 기준(동시 채널 수 등)을 따로 정할 필요가 있다.

## A1 보낸 채팅 — 가능

user_id별 총 채팅 수·순위·백분위 모두 산출된다. 전체 유저 343,298명, 분포는 p50=11 / p90=278 / p99=1,925 / 최대 33,740.

표본 유저 순위·백분위:

| uid | total_msgs | 순위 | 백분위 |
|---|---|---|---|
| ECD2847E… | 33,740 | 1 | 100 |
| 1E5ED2A8… | 33,117 | 2 | 99.9997 |
| 40588DD1… | 28,868 | 3 | 99.9994 |
| 08F3A5B8… | 27,851 | 4 | 99.9991 |
| D1BF1B56… | 26,947 | 5 | 99.9988 |

**모수 안정성**: 총 1건 유저가 56,813명(16.5%), 5건 이하가 130,885명(38.1%)이다. 전체를 모수로 잡으면 하위 구간에서 대규모 동순위가 생기고, 신규 적재 며칠 만에 백분위가 크게 출렁인다. 순위·백분위 표시는 최소 활동 기준(예: 총 5건 이상 또는 활동 2일 이상)을 둔 모수에서 계산하는 편이 안정적이다. 상위권은 1~5위 간격이 600~1,000건 수준으로 벌어져 있어 순위 자체는 안정적이다.

막는 것: 없음. 실행 질의:

```sql
WITH per_user AS (
  SELECT user_id, sum(mc) AS total_msgs
  FROM (
    SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
    FROM chat_trace GROUP BY channel_id, bucket_at, user_id
  )
  GROUP BY user_id
),
ranked AS (
  SELECT user_id, total_msgs,
         rank() OVER (ORDER BY total_msgs DESC) AS rnk,
         count() OVER () AS n
  FROM per_user
)
SELECT hex(user_id), total_msgs, rnk, round(100.0 * (1 - (rnk - 1) / n), 4) AS pctl
FROM ranked WHERE user_id IN (...) ORDER BY rnk
-- 분포 통계는 같은 per_user 에서 quantile/countIf 로 산출 (12.6초)
```

## A2 머문 채널 — 가능

uniqExact(channel_id) per user. 6.1초. 분포(343,300명): 1채널 176,171명(51.3%), 2채널 56,570명, 3채널 30,317명, 4~9채널 60,090명, 10채널 이상 20,152명(5.9%). p50=1, p90=7, 최대 165.

표본: 1E5E=158, 08F3=7, 4058=6, D1BF=4, ECD2=1. 상위 발화자라고 다채널은 아니다(1위 유저는 단일 채널).

막는 것: 없음. 실행 질의:

```sql
SELECT user_id, uniqExact(channel_id) AS ch_cnt
FROM (SELECT channel_id, bucket_at, user_id FROM chat_trace GROUP BY channel_id, bucket_at, user_id)
GROUP BY user_id
-- uniq 계열은 중복 접기 없이도 값이 같지만 위 형태로 통일
```

## A3 함께한 분 — 가능

uniqExact(bucket_at) per user와 분당 말수(total_msgs / mins). 11.2초. 분포: 활동 분 p50=9 / p90=183 / 최대 8,232. 분당 말수 p50=1.17 / 평균 1.33 / p99=3.00.

표본:

| uid | 활동 분 | 채널-분 | 총 채팅 | 분당 말수 |
|---|---|---|---|---|
| 1E5ED2A8… | 8,232 | 18,332 | 33,122 | 4.02 |
| 40588DD1… | 4,368 | 4,370 | 28,868 | 6.61 |
| 08F3A5B8… | 3,888 | 3,888 | 27,855 | 7.16 |
| ECD2847E… | 3,088 | 3,088 | 33,751 | 10.93 |
| D1BF1B56… | 2,774 | 2,774 | 26,958 | 9.72 |

**정의 주의**: 같은 분에 여러 채널에서 발화한 유저가 21,614명 있다. distinct bucket_at(달력상 분)로 세면 이들의 "함께한 분"이 채널-분 합보다 작아지고 분당 말수가 부풀려진다(1E5E: 4.02 vs 채널-분 기준 1.81). 리캡 정의를 "달력상 분"과 "채널-분" 중 하나로 명시해야 한다. 일반 유저는 두 값이 사실상 같다.

막는 것: 없음. 실행 질의:

```sql
SELECT user_id, uniqExact(bucket_at) AS mins, uniqExact(channel_id, bucket_at) AS ch_mins, sum(mc) AS total_msgs
FROM (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace GROUP BY channel_id, bucket_at, user_id
)
GROUP BY user_id
```

## A4 함께한 방송 — 가능

chat_trace의 live_id는 접은 뒤 기준 25,345,533행 전부 0이 아니다(zero 0%). 방송 5,384개가 전부 단일 채널에만 귀속되어(복수 채널에 걸친 live_id 0건) 채널-방송 매핑도 일관적이다. live_census의 live_id 채움 47%와 무관하게, chat_trace 단독으로 uniq(live_id)를 신뢰할 수 있다.

유저당 방송 수 분포: p50=3 / p90=14 / 최대 585. 표본: 1E5E=585, 4058=21, 08F3=20, D1BF=11, ECD2=8.

막는 것: 없음. 단, live_census와 조인해 방송 제목·카테고리를 붙이는 경우엔 live_census의 live_id 채움 47%가 제약이 된다(이 조각 자체는 chat_trace만으로 충분). 실행 질의:

```sql
SELECT countIf(ch_cnt > 1), count()
FROM (SELECT live_id, uniqExact(channel_id) AS ch_cnt FROM chat_trace GROUP BY live_id);

SELECT user_id, uniqExact(live_id) FROM chat_trace GROUP BY user_id
```

## B1 쏠림 — 가능

유저별 채널 상위 N 지분. 7.3초. 2채널 이상 유저 167,171명의 top1 지분: 평균 64.4%, 중앙값 66.0%. 4채널 이상 유저 80,257명의 top3 지분: 평균 85.2%, 중앙값 88.9%. 다채널 유저도 대부분 한두 채널에 쏠려 있어 서사가 성립한다.

표본(상위 3채널 지분): 4058 = 91.4/8.5/0.1%, D1BF = 99.5/0.5/0.0%, 1E5E = 8.9/8.6/7.7%(봇 성격, 균등 분산).

막는 것: 없음. 실행 질의:

```sql
WITH user_channel AS (
  SELECT user_id, channel_id, sum(mc) AS msgs
  FROM (
    SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
    FROM chat_trace GROUP BY channel_id, bucket_at, user_id
  )
  GROUP BY user_id, channel_id
)
SELECT user_id, sum(msgs) AS total,
  arraySum(arraySlice(arrayReverseSort(groupArray(msgs)), 1, 3)) AS top3
FROM user_channel GROUP BY user_id
-- 표본 확인은 sum(mc) OVER (PARTITION BY user_id) 창함수 + LIMIT 3 BY user_id
```

## B2 지분 덩어리 — 가능 (B1과 동일 값)

B1의 user_channel 집계에서 지분 배열을 그대로 시각화하는 조각이다. 별도 원천이나 추가 컬럼이 없으므로 별도 검증은 불필요하고, B1이 가능하면 B2도 가능하다.

## B3 첫 만남 — 부분 가능

유저-채널별 min(bucket_at)은 계산된다(0.4초). 그러나 첫 등장일 분포가 수집 개시에 절단되어 있다: 전체 유저-채널 쌍 1,031,893개 중 08-22에 124,080쌍(12.0%), 08-23에 205,844쌍(19.9%)이 몰려 있다. 08-21 이전은 176쌍뿐이다.

표본에서도 4058·D1BF의 주력 채널 첫 만남이 모두 08-22 18:2x — 실제 첫 만남이 아니라 수집 시작 시각이다. "처음 만난 날" 서사로 쓰면 대부분의 유저에게 거짓 날짜를 보여주게 된다.

막는 것: 수집 기간 부족(좌측 절단). 수집이 계속되면 신규 유저-채널 쌍에 한해 진짜 첫 만남이 기록되므로, "수집 개시(08-22) 이후 처음 만난 채널"로 문구를 한정하면 지금도 쓸 수 있고, 무제한 서사는 수개월 축적 후에 풀린다. 실행 질의:

```sql
SELECT toDate(first_at) AS first_day, count()
FROM (SELECT user_id, channel_id, min(bucket_at) AS first_at FROM chat_trace GROUP BY user_id, channel_id)
GROUP BY first_day ORDER BY first_day
```

## B4 갈아탄 밤 — 가능

하루(Asia/Seoul 기준 toDate)에 2채널 이상 채팅한 날 수. 0.9초. 유저 343,397명 중 124,715명(36.3%)이 그런 날을 1일 이상 보유. 분포 p50=0 / p90=4 / 최대 9(실질 9일이므로 매일).

표본: 1E5E=9/9일, 08F3=8/9일, 4058=7/9일, D1BF=3/9일, ECD2=0/9일.

서버 타임존이 Asia/Seoul이므로 "밤"을 시간대(예: 22~04시)로 한정하는 변형도 toHour(bucket_at)로 바로 가능하다. 막는 것: 없음(실질 9일이라 "날 수" 최대치가 작다는 점만 유의). 실행 질의:

```sql
SELECT user_id, count() AS active_days, countIf(chans >= 2) AS switch_days
FROM (
  SELECT user_id, toDate(bucket_at) AS d, uniqExact(channel_id) AS chans
  FROM chat_trace GROUP BY user_id, d
)
GROUP BY user_id
```

## B5 채널 교차 — 가능

**by_user 프로젝션은 실제로 쓰인다.** user_id 필터 질의의 EXPLAIN indexes=1 결과가 `ReadFromMergeTree (by_user)`, PrimaryKey Keys에 user_id, 3,102 granule 중 7개만 읽음(binary search)으로 나왔다. 유저 단건 조회는 0.1초대다.

쌍 집계 비용: 2채널 이상 유저 167,171명의 채널 집합에서 조합을 펼쳐 전 쌍을 집계하는 데 1.3~2.5초. 쌍 전개 행 3,757,658행, 유효 쌍 266,598개. 상위 쌍은 공유 유저 5,266명 수준. 쌍 집계는 GROUP BY user_id 경로라 프로젝션 이득은 없지만 비용 자체가 작다.

막는 것: 없음. 실행 질의:

```sql
EXPLAIN indexes = 1
SELECT channel_id, bucket_at, msg_count FROM chat_trace WHERE user_id = unhex('4058…');

WITH user_chans AS (
  SELECT user_id, groupUniqArray(channel_id) AS chans
  FROM chat_trace GROUP BY user_id HAVING length(chans) >= 2
)
SELECT least(pair.1, pair.2) AS ch_a, greatest(pair.1, pair.2) AS ch_b, count() AS shared_users
FROM user_chans
ARRAY JOIN arrayFilter(p -> p.1 < p.2,
  arrayFlatten(arrayMap(i -> arrayMap(j -> (chans[i], chans[j]),
    range(1, length(chans)+1)), range(1, length(chans)+1)))) AS pair
GROUP BY ch_a, ch_b ORDER BY shared_users DESC
```

## B6 달라진 것 — 지금은 불가

반기 차는 원천적으로 불성립(단일 월). 대체 단위 검증 결과:

- 주 단위: toMonday 기준 유의미한 주가 2026-08-17 주(452만 행)와 08-24 주(2,087만 행) 둘뿐인데, 첫 주는 실제로 08-22~23 주말 이틀만 담고 있다. 이틀(주말) vs 7일(한 주 전체)의 비교라 "달라졌다"는 서사가 커버리지 차이의 산물이 된다. 표본 유저도 값은 나오지만(4058: 6,356→22,512건) 해석이 불가능하다.
- 전반/후반 분할(08-22~25 vs 08-26~30): 형태는 만들 수 있으나 4일 vs 5일이고 요일 구성이 달라 같은 왜곡이 남는다.

막는 것: 기간 부족. 온전한 주가 2개 쌓이는 2026-09-07경부터 주 단위 비교가 성립하고, 월 단위는 10월, 반기는 내년에 풀린다. 실행 질의:

```sql
SELECT toMonday(bucket_at) AS wk, count(), uniqExact(user_id), uniqExact(channel_id)
FROM chat_trace GROUP BY wk ORDER BY wk
```

## B7 월별 구성 — 지금은 불가

toYYYYMM 기준 202608 하나뿐이라 월별 구성이 성립하지 않는다. 주 단위 대체도 B6과 같은 이유로 아직 왜곡된다. 지금 쓸 수 있는 대체는 일 단위(9일) 또는 요일 단위 구성 정도인데, 요일도 각 요일이 1~2회밖에 없어 "이번 리캡 기간의 하루하루" 정도의 서사만 가능하다.

막는 것: 기간 부족. 2개월째인 2026-10-01부터 월별 2점 비교, 연말 리캡 시점엔 4~5개월 구성이 가능하다. 실행 질의:

```sql
SELECT toYYYYMM(bucket_at) AS ym, count() FROM chat_trace GROUP BY ym ORDER BY ym
```

## B8 이 방에서의 나 — 가능

유저-채널별 분당 말수(msgs / distinct bucket). 6.3초. 유저-채널 쌍 1,032,005개, 분당 말수 p50=1.09 / p90=2.0 / p99=3.0.

표본(4058): 주력 채널 6.86/분(3,846분), 부채널 4.86/분(504분). (D1BF): 주력 9.9/분(2,711분).

**표시 기준 필요**: 쌍의 54.4%가 활동 5분 미만이다. 2분 활동에 7건이면 3.5/분처럼 소표본 값이 과장되므로, 리캡에는 최소 체류(예: 30분 이상) 채널만 이 조각을 보여주는 기준이 필요하다.

막는 것: 없음. 실행 질의:

```sql
SELECT user_id, channel_id, sum(mc) AS msgs, uniqExact(bucket_at) AS mins,
  round(sum(mc) / uniqExact(bucket_at), 2) AS msgs_per_min
FROM (
  SELECT channel_id, bucket_at, user_id, argMax(msg_count, ingested_at) AS mc
  FROM chat_trace GROUP BY channel_id, bucket_at, user_id
)
GROUP BY user_id, channel_id
```
